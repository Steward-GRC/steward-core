# API

The API is `steward.core.v1`, in [`proto/steward/core/v1`](../proto/steward/core/v1), with the Go
stubs committed in `gen/go`. Access to every RPC is enforced at the gateway; core records the
`actor_user_id` a request names. Errors carry an `ErrorInfo` ([error codes](error-codes.md)).

| Service | Holds |
| --- | --- |
| `CategoryService` | The category tree, governance and its inheritance, and the ordered access rules. Each rule is one row with a tri-state cell (blank, `allow`, `deny`) per action: `read`, `ack`, `approve`, `author` and `manage` (move and reorder documents in the categories the subject has access to). `SetCategoryRuleset` validates the rules (subject, grants) and checks `manage` like the other cells (blank, `allow` or `deny`); a rule with only a `manage` cell is valid. Core stores and returns `manage` and applies no semantics to it: the access engine reads it, not core. A category that has no rules at migration time gets one rule, Everyone: Read (migration 0034, run once), as a new category does. `GetEffectiveRuleset(category_id)` returns the whole chain in one call: `levels`, one `EffectiveLevel` (`category_id`, `name`, `owners` as stored, `rules` in ordinal order with all five cells, `manage` included) per category, the category itself first and then each ancestor up to the top-level one. The levels come from one recursive query, so they are one consistent snapshot, not a read per level; the walk is capped at the category depth limit and never revisits a category. A category with no rules is still a level, with empty `rules`; an unknown category is `NOT_FOUND`. Core evaluates nothing and stores nothing new: the access engine decides from these inputs. The gateway (on behalf of the user), `obligations`, `workflow` and `collab` (as themselves) may call it. `PurgeUserCategoryRules` removes a deleted user's rules. Siblings have a stored order (`order_index`, from zero under each parent): a new category and a moved one go last, `ReorderCategories` sets the order of one parent's children (empty `parent_id` for the roots) from a list that holds every child exactly once, and `ListCategoryChildren` returns them in that order. A category says which document types it takes (`document_types`: both, the default, policies, procedures, or none for a container of child categories); it is the category's own setting and a child does not inherit it. `CreatePolicy` and `MovePolicy` refuse a type the category does not take with `CATEGORY_REFUSES_TYPE`, `SetCategoryDocumentTypes` refuses a narrowing while live documents of a removed type are in the category with `CATEGORY_HOLDS_DOCUMENTS` (the total and per-type counts are in the error metadata), and `CountCategoryDocuments` counts a category's live policies and procedures. |
| `PolicyService` | Policies and procedures: drafts, publish, versions, diffs, templates, sensitivity, rename, move, owners, acknowledgement settings and reindexing. `ListPoliciesByOwner(owner_user_id, include_retired)` returns the policies a user owns, each with `current_draft_version_id` set to its draft or in-review version (the same lookup as `GetPolicy`, empty when it has none), which is how the gateway's `myDrafts` tells the owner's drafts apart (core#121). `DiffVersions(from_version_id, to_version_id)` returns one `SectionDiff` per section: when both versions pin a template version, the sections of the "to" version's template in its order (a migration marks changed sections boilerplate); when either has no template version (a freeform version, or a freeform one against a templated one), one per content block, never boilerplate, where a heading starts a block keyed by a slug of its text (`-2`, `-3` for repeats by order, `section` for an empty heading) and titled by it, and text before the first heading is the block `body` titled `Introduction`. Block diffs are in the "to" order, with a block only the "from" side has (`removed`) right after the block it followed there. A diff of two published versions is cached by the pair. `SearchPolicies(query, document_type, limit, offset)` finds documents by the words in their title, number and published text (the latest published row of each live appendix included): every word must match, as a whole word, ignoring case, with no stemming and no stop words. It never matches a draft, a version in review, a superseded version or a retired document. A hit carries the `Policy`, a `rank` (a title or number hit outranks a text-only hit; comparable within one search only), `title_match` and `title_rank` (the query matched the title and number alone, which is all the gateway may tell a reader whose content is obfuscated) and a `snippet`: plain text with `matches` counted in UTF-16 code units, at most 170 characters with an ellipsis at a cut end, unset when no word matched the text. `limit` is 1 to 100 (0 means 20, more is 100), `offset` skips hits, `has_more` says another page follows; a blank query finds nothing, a query over 256 characters or a negative `limit` or `offset` is `InvalidArgument`. Core applies no read rule: the gateway filters the hits by the reader's read decision. The index is the `policy_search` table, kept by database triggers from every write path. Neither the query nor any policy text is logged, only the query's length. Semantic versions (core#28): every numbered policy version carries `semantic_version` (MAJOR.MINOR.FIX) beside `version_no`, which stays its ordinal. The number is written when the version is published, by either publish path, from the highest numbered version bumped by the change type the version publishes as; the first version is 1.0.0 and migration 0036 backfilled earlier versions as `version_no`.0.0. A draft or a version in review reports the number a publish would give it from its content as it is now (nothing is stored); `SaveDraft` leaves it unset. The change type is classified against the highest numbered version: a different template, a switch to or from freeform, a required template section added, dropped or turned required, or a changed word that is a number, date, amount or obligation word (must, shall, may, should, not, within, days and so on) is `MAJOR`; an optional section added or dropped, or more than 10 changed words, is `MINOR`; anything smaller is `FIX`; unreadable content is `MAJOR`. Scope, audience and sensitivity belong to the document, not to a version, so they are not compared. The classification is stored at submit (`SetVersionStatus` to `in_review`) and again at publish, since a version in review stays editable. The author may raise the type freely, in `SetVersionStatus` (`change_type`, `change_type_reason`) or `SetVersionChangeType`; a pick below the suggestion needs a reason (`InvalidArgument` without one, and a refused submit leaves the draft a draft) and is stored as `requested_change_type`: the version keeps the suggested type until workflow calls `RecordChangeTypeAgreement(policy_version_id, agreed_by_user_ids, actor_user_id)`, which applies the lowering and stores who agreed (workflow only; `FailedPrecondition` when nothing is pending). An edit after the agreement that makes the change bigger than what was agreed to is not covered by it. The first version takes no pick. `ListObligatingPolicies` carries `semantic_version` and `change_type` of the published version, and the published lifecycle event carries `Semver` and `ChangeType`. Audit: `policy.status_set` (with the suggested and set types at submit and the number at publish), `policy.change_type_set` and `policy.change_type_agreed`. |
| `TemplateService` | Templates and their versions. A template version carries `semantic_version` and `change_type`, written when it is published from the change against the highest numbered published version (the first is 1.0.0, earlier versions were backfilled `version_no`.0.0): a required section added, dropped or turned required is `MAJOR`, an optional section added or dropped, or changed boilerplate text, is `MINOR`, and titles, order and heading level alone are `FIX`. A draft reports what a publish would give it now. `published_at` dates the version (unset for a draft) and `Template.updated_at` is the latest of a rename and any version being created or published. |
| `AppendixService` | Appendices of a draft version. |
| `PolicyAppendixService` | The appendices a policy or procedure owns, which belong to the document and not to one of its versions. Each has a version table of its own: at most one `DRAFT` beside the `PUBLISHED` history, and readers see the latest published row. `ListPolicyAppendices` returns the live appendices in order (the retired ones after them with `include_retired`), each with `published`, `draft`, `versions` (oldest first), `published_versions` (newest first, no draft) and `contributor_ids` (everyone who saved or published, each once, in first-save order); the letter (A, B, C) follows the order of the live appendices and is empty while retired. `GetPolicyAppendix` returns one appendix by `id` in the same shape, a retired one included (its letter is empty); an unknown id is `NotFound` and a malformed one `InvalidArgument`, and it is a read that writes no audit event. `CreatePolicyAppendix` starts a draft v1 last in the order, with a blank title becoming `Appendix <letter>` and skipping any title the policy's appendices (retired included) already use. `SaveAppendixDraft` updates the open draft or starts draft vN+1 beside the published row, and a save equal to the published title and content with no draft open makes none. `PublishAppendix` promotes the draft to the next published version. `RetireAppendix` hides an appendix and keeps its history, `RestoreAppendix` puts it back last in the order; neither makes a draft. `ReorderPolicyAppendices(policy_id, ordered_ids)` sets the order of the live appendices and returns them in the new order with their letters: `ordered_ids` must hold every live (not retired) appendix of the policy exactly once, and a missing, repeated, foreign, retired or unknown id is `InvalidArgument` and changes nothing (an unknown policy is `NotFound`). Retired appendices keep no letter and stay out of the order, and a reorder makes no draft and touches no version row. `DiffPolicyAppendix(id, optional content_json)` returns the `SectionDiff` list (the one `PolicyService.DiffVersions` returns) of what is published against what would replace it: `from` is the published row's content (empty when none is published) and `to` is `content_json` when given (text the author has not saved), else the draft's content, else the published row's. An appendix has no template, so the sections are the union of the section keys of both sides, in key order, and a section that did not change reads `unchanged`; an appendix diffed against itself has no changed section. A supplied `content_json` is checked like a save (`InvalidArgument` when it is not valid JSON or not readable appendix content); an unknown id is `NotFound`, a malformed one `InvalidArgument`, and a retired appendix can still be diffed. It is a read: nothing is saved, no draft appears, the stored draft is left alone, and it writes no audit event and caches nothing. `CheckpointAppendixDraft(id, policy_id, content_json, actor_user_id)` is how the collab room saves an appendix's text on behalf of the person editing, and returns `{accepted, reject_reason}`: it takes no title (an open draft keeps its own, a new draft takes the published row's), updates the open draft or starts draft vN+1, makes no draft when the content equals the published row with none open (accepted, nothing written), records the actor as a contributor once and writes the same `appendix.saved` event as a draft save. Content that is not a JSON document is a refusal (`accepted=false` with a `reject_reason`, nothing stored), a `policy_id` that is not the appendix's is `InvalidArgument`, an unknown `id` is `NotFound`, and a retired appendix is `FailedPrecondition`, as `UpdateDraftContent` answers a version that is no longer the working copy. The collab service may call it on behalf of the editing user, and may call `GetPolicyAppendix` as itself (to resolve an appendix's policy when it issues an appendix room token); it may call no other `PolicyAppendixService` method. `DeletePolicyAppendix(id, actor_user_id)` removes a retired appendix, every row of its version table (the draft included) and its history for good, and returns an empty response and writes one `appendix.deleted` event (ids and version numbers, no title or text). An appendix that is not retired is `FailedPrecondition`, an unknown id is `NotFound`, and a malformed `id` or `actor_user_id` is `InvalidArgument`; each leaves everything as it was. Core applies no role rule here: only a site admin may delete for good, and the gateway checks that before it calls. Only the gateway, on behalf of the signed-in user, may call it. Saving or publishing a retired appendix is `FailedPrecondition`, as is publishing with no draft. Core applies no role or reader filtering: it returns the published row and the draft side by side and the gateway decides who sees the draft. Every write names its `actor_user_id`. `AppendixService` and its tables are unchanged. |
| `VersionLinkService` | The library links of a policy version: definitions, references, contact blocks and related policies. The library items are not versioned; the links are, so they go through approval with the version, stay as approved once it is published and are copied into a new draft by `PolicyService.SaveDraft` (and by the draft a rename stages) from the version the appendices copy from. `GetVersionLinks` returns definitions alphabetically, references and contact blocks in the order they were set (each with `used_by_count`), and `related`: the version's own links (`OUTGOING`) followed by the links other policies make to this one (`INCOMING`, read as the inverse type), taken from the published version of the naming policy, so a link in someone's draft shows on the other side only once that draft is published. `editable` is status only (the version is a draft or in review); the caller's permission is the gateway's to check. The four `SetVersion*` calls each replace one kind of link and return the version's links: `FailedPrecondition` for a version that is published, superseded, rejected or archived (linking never creates a draft), `InvalidArgument` for an id named twice, an unknown relationship type, a link to the version's own policy or a repeated policy and type, `NotFound` for a version, library item or policy that does not exist. `ListRelationshipTypes` is a fixed list of five pairs, each with its inverse. A definition title is unique across categories ignoring case and surrounding spaces: `CreateDefinitionEntry` and `UpdateDefinitionEntry` return `AlreadyExists` for a taken title and `InvalidArgument` for an empty one. `RelationService` and the per-document attachment calls are unchanged until the gateway moves. |
| `RelationService` | Related links: a flat, one-way list per document. |
| `ReviewService` | Inline review threads on a policy version, each with one approver, and suggested changes with counters and outcomes on a thread; the gateway passes `actor_user_id` and `actor_side`. |
| `SettingsService` | The global settings and the keyless email-service status. The global settings hold the two banners and the one site-wide work calendar (`WorkCalendar`: ISO `weekdays` 1 Monday to 7 Sunday, an IANA `timezone`, and `holidays` of `Holiday{date YYYY-MM-DD, label}`; whole days only; defaults Monday to Friday, UTC, no holidays). `GetGlobalSettings` always returns the effective calendar; the gateway (on behalf of the user) and `workflow` (as itself, to read the calendar when a document is submitted) may call it, and `workflow` may call no other settings method. `SetGlobalSettings` replaces it only when `work_calendar` is present; an absent one leaves it unchanged (the banners are always replaced). A calendar with no working weekday, a bad or repeated weekday, an unloadable zone (`""` and `Local` are refused), a holiday that is not a real, unique `YYYY-MM-DD` date, more than 366 holidays or a label over 80 characters is `INVALID_WORK_CALENDAR` (`InvalidArgument`) and nothing is written. A real change also emits the audit event `global_settings.work_calendar_updated` (before and after weekdays and zone, holiday counts, the dates added, removed or relabeled; never the labels). |
| `EmailServiceSecretService` | Internal only: the email-service configuration with its key, for the service that sends mail. The gateway never serves it. |
| `AssetService` | Editor images and files: upload, get, the admin setting of which kinds of file are accepted, and the admin list of stored files (with the documents that link to each, or only the unlinked ones) and delete. A delete removes the bytes, the record and the file card from every document that links to it, with no new version; the only record is the `asset.deleted` audit entry. |

The server also serves `grpc.health.v1` and reflection. On `grpc.health.v1`, `liveness` reports the
process only, and the empty name and `readiness` fail while Postgres or RabbitMQ is down. Every
`Health/Check` answer carries the `steward-version`, `steward-commit`, `steward-dep-<name>` and
`steward-depstate-<name>` headers. `/livez` and `/readyz` serve the same over HTTP on
`PROBE_PORT`; see the [runbook](runbook.md#probes).

## Events out

**Audit.** Every change publishes a `steward.audit.v1.AuditEvent` (steward-audit's contract) to the
`audit` topic exchange, as protobuf binary with the content type
`application/protobuf; proto=steward.audit.v1.AuditEvent` and the routing key `audit.audit`.
Actions are dotted verbs such as `category.created`, `category_rule.updated`, `policy.published`,
`appendix.created`, `appendix.saved`, `appendix.published`, `appendix.retired`, `appendix.restored`, `appendix.reordered`, `appendix.deleted`
and `email_service_config.updated`. No event carries a secret or document content.
`category.governance_updated` is emitted only when governance changed. It carries the new value of
`owners`, `audience_group_ids`, `exclusion_group_ids`, `ack_triggers`, `review_cadence`,
`review_date` and `ack_everyone`, and the old value of each as `prev_<key>`. Owners are user uuids,
lists are sorted and comma-joined, `none` is an explicit empty value and `inherit` is not set here.

**Lifecycle.** JSON events on the `jobs` topic exchange, for the services that act on documents:

| Routing key | When |
| --- | --- |
| `policy.published`, `procedure.published` | A version is published, with its section text for indexing. |
| `policy.retired`, `procedure.retired` | A document is retired. |
| `policy.obligation_changed` | A change that may alter who must acknowledge a policy. |
| `policy.break_glass_read` | A document (policy or procedure) was read under a break-glass grant. Obligations tells its owner and the compliance admins. Unique `event_id` per read. |

Reindexing sends the published content straight to the AI indexer's queues (`ai.policy.publish`,
`ai.procedure.publish`) through the default exchange, so other `jobs` consumers don't see it again.

## Break-glass reads

A site admin who would see a document obfuscated can ask identity for a time-boxed break-glass grant
on that one document (the gateway's `breakGlassReveal`). The gateway honours an active grant for that
document only, and before it serves the content it calls `PolicyService.RecordBreakGlassRead` with
the policy id and, for a single version, the version id. The reader is the forwarded actor.

Core then:

- records `policy.break_glass_read` in the audit tier, with the policy number and version id. During
  act-as the actor is the real admin and `impersonated_user_id` names the user acted as, as for every
  other event;
- publishes `policy.break_glass_read` on `jobs` with the document, its owner, the reader and, during
  act-as, the admin.

Both must succeed. If either publish fails, or the service runs without the audit or jobs
publisher, the call is `Unavailable` and the gateway serves nothing: a break-glass read is never
served unrecorded. A version id that belongs to another policy is `InvalidArgument`, and a call
with no forwarded actor is `Unauthenticated`.

## Calling other services

Core calls no other service. It uses one other service's contract: steward-audit's `AuditEvent`,
pinned by commit in [`proto-refs.env`](../proto-refs.env). `scripts/proto-generate.sh` fetches that
proto into the git-ignored `.protos/` and generates `gen/go/thirdparty/audit/v1`; only the stubs are
committed. To try an unmerged audit change, set `STEWARD_AUDIT_PROTO_DIR` to its `proto/` directory.
